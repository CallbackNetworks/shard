# ADR-0128: 決策的關係圖是一個可以動手的檢視，而不是一張圖片

## Status
Accepted

## Date
2026-08-29

## Context

使用者問「沒有那種 Dependencies graph 嗎？我在考慮作為直接顯示主要觀察介面」，並列出四個
想從圖上看出來的東西：

1. 這個決策管到哪些工作
2. 這個工作是依什麼決定的
3. 想法怎麼演進到現在
4. 哪些決策彼此矛盾／有前提關係

盤點下來，第 4 項在資料模型裡不存在（ADR-0127 補上了）。其餘三項的狀況是：

- **已經有一個 graph**：`/structure`（側欄 Hierarchy）有 NETWORK 佈局，還有一個獨立的
  `MAP / DEPENDENCIES` 模式和一張 DEPENDENCIES 統計卡。但那個 DEPENDENCIES 畫的是
  `depends_on`，依 ADR-0078 的宣告是 `task → task`，跟決策無關。
- **決策確實會出現在 NETWORK 佈局裡**，`supersedes` / `governs` 自 ADR-0118 起也會走通用
  custom-link 路徑被畫出來——**但那條 lane 用 `status !== 'proposed'` 把已定案的決策濾掉了**，
  註解寫「settled decisions are noise there」。正式站的 2 條 `supersedes` 邊，兩端都是已定案
  的記錄，所以資料庫裡唯一的那段決策史在這張圖上**永遠畫不出來**。後面還有一個 `.slice(0, 18)`。
- **第 2 項（工作那一側）根本沒有寫入入口**。`governs` 在整個 app 裡只有一個建立控制項，
  在決策那一側；而這件事幾乎總是從工作那頭被想起來的（「我為什麼在做這個？」）。正式站
  103 筆決策只有 1 條 `governs` 邊。

## Decision

**三件事，一起做，因為單獨做任何一件都不會讓圖有東西看。**

### 一、`governs` 從工作那一側也建得起來

`components/GoverningDecisions.jsx` 從唯讀變成可寫（`editable`），掛在 `/n/{id}` 與
`MembershipPanel` 上。唯讀時它在「沒有東西管這個節點」時不畫任何東西——那是對的，那時它純粹
是輸出，每個節點都掛一列空標題就是噪音。**可寫時空狀態才是重點**：那是唯一會提供這個連結的
東西，把它藏起來等於把建立入口也一起藏了。邊仍然是 `decision → work`，不管你從哪一頭進來。

### 二、決策頁多一個 graph 模式

`utils/decisionGraph.js` + `components/decisions/DecisionGraph.jsx`。

**兩條帶狀分層，不是力導向。** 力導向回答的是「這些有沒有聚在一起」；這裡要回答的四個問題
全都是有方向的，而分層圖用**位置**回答它們——欄位 0 是地基，順著箭頭往右走就是從前提走到結論；
下面那一帶是它決定的工作。彈簧模擬會主動破壞這個訊息。佈局是決定性的：同樣的輸入永遠畫出
同一張圖。

**沒有關係的記錄預設不畫，而且會被數出來。** 圖講的是關係；一筆沒有關係的記錄是一列，而
清單模式就是列住的地方。「99 筆沒有任何關係」是這一頁對一百筆記錄能講的最有用的一句話，
所以它是一顆寫著數字的按鈕，不是一個安靜的過濾。

**選一個節點會把它碰不到的東西調暗，並在下方畫出那筆記錄的卡片**——就是清單模式用的同一張
`DecisionCard`。一張不能動手的圖是一張圖片，而那正是 `governs` 在 ADR-0118 整個生命週期裡的
處境。關係的建立走既有的控制項，不另外做一套。

**顏色不用來分關係。** 這一頁的顏色已經花在決策狀態上（ADR-0088），關係用線型和字符來分。
只有 `conflicts_with` 拿到重量（粗紅線），因為它是這張畫布上唯一「是個問題」而不是「是個事實」
的關係。`conflicts_with` **不畫箭頭**：主張是對稱的，而那一列在儲存上仍然是有向的（ADR-0127），
畫出那個方向等於說了資料沒有說的話。

### 三、修好 `/structure` 已經有的那一個

「已定案的決策是噪音」這句話，在決策唯一的關係只是「屬於某個專案」的時候是對的——它同時
安靜地刪掉了相反的情況。**一個被畫在畫面上的邊指到的節點，就是「不是噪音」的定義。** 所以
lane 的過濾改成：已定案但是關係端點的決策留下；`.slice()` 也先保留這些端點再截斷其餘的，
因為砍掉一個邊指向的節點，會留下一條指向空氣的線。

順手修掉一個只有把它掛到別處才會發現的問題：`.kt-map-segment` 的內距與 `is-active` 樣式
一直是從 `.kt-map-toolbar button` 繼承來的。第一次把它掛在別的頁面（這裡的清單／關係圖切換）
上，標籤就跟圖示疊在一起，而且選中的那半跟沒選中的長得一樣。樣式現在由 segment 自己帶。

## Consequences

正面：

- 四個問題各有一個地方回答：`governs`（兩個方向都可寫）、`supersedes` + `requires` 的分層、
  `conflicts_with` 的粗紅線。
- 正式站那唯一一段決策史，第一次會出現在 `/structure` 上。
- 圖可以動手：選一個節點就拿到那筆記錄的完整控制項，所以「看到缺一條邊」跟「補上那條邊」
  之間沒有換頁。

負面與取捨：

- 又一個佈局引擎。`buildNetworkLayout` 跟結構圖自己的形狀（identity／project／task／lane）
  綁得很緊，硬要共用會是把兩張圖的需求塞進一個函式。共用的是弧線路徑的形狀，所以同一個 app
  裡的兩張圖不會用兩種方式畫一條邊。
- 圖模式會蓋掉待審佇列與演進兩欄。主控台留著，因為它的過濾與計分板在兩個模式下描述的是同
  一個集合——複製一份 graph 專用的側欄就是同一件事有兩個控制項。
- 有很多關係之後這張圖會變寬。畫布在自己的框裡捲動（ADR-0088 的規則：寬內容自己捲，頁面本體
  不橫捲），但**沒有做縮放或平移**。要是哪天真的有幾百條邊，那會是下一條 ADR 的題目，不是
  現在先蓋好放著的機制。
- `GoverningDecisions` 現在在每個掛載它的地方都會畫出來（因為兩處都是可寫的）。這是刻意的：
  那兩個地方都是「看這個節點的關係」的畫面，一列寫著「還沒有 ＋連結」是資訊，不是噪音。
