# ADR-0160: 元件要得到的 key，必須是語言檔真的有的 key

## Status
Accepted

## Date
2026-09-11

## Context

[ADR-0088](0088-a-colour-means-one-thing.md) 立了「每一個會顯示文字的畫面都必須可翻譯」，
並且用 `src/__tests__/i18nCoverage.test.js` 兩個守衛釘住：

1. 每個 `pages/` / `components/` 底下的檔案都要呼叫翻譯器。
2. `en.json` 與 `zh-TW.json` 要描述同一個 app。

兩個守衛都通過的情況下，`t('pwa.install')` 仍然可以指向一個**兩份語言檔都沒有**的 key：
第一個守衛看的是「有沒有呼叫」，不是「要的是什麼」；第二個守衛看的是兩份檔案一不一致，
而它們確實一致——一致地都沒有這個 key。

i18next 對找不到的 key 的行為是**把 key 本身印出來**。這個缺陷實際發生過一次：Settings
頁上一顆按鈕在真實瀏覽器裡字面寫著 `SETTINGS.SAVE`，因為 `t('settings.save')` 不存在
（真正的 key 是頂層的 `save`）。元件測試把 `t` mock 成 identity function，所以對它而言
對的 key 跟錯的 key 沒有差別；ADR-0088 的兩個守衛也照樣綠燈。當時的結論是「這一類只有真
瀏覽器抓得到」。

這次掃了全部呼叫點，找到三個活著的：`common.close`、`pwa.install`、`pwa.installPrompt`。
三個都沒有變成 `COMMON.CLOSE` 印在畫面上，因為它們都帶了**位置參數形式的英文預設值**
（`t('pwa.install', 'Install')`）。也就是說，它們不是壞掉，而是**在每一種語言底下都渲染
英文**——正好就是 ADR-0088 要終結的那件事，只是穿了一件呼叫翻譯器的外衣。

## Decision

加第三個守衛，補上前兩個看不到的那個方向：掃 `pages/` / `components/` 裡所有字面 key 的
`t('...')` 呼叫點，經過複數字尾（`_one`/`_other`/…）還原之後，必須在**任一**語言檔裡找得到。

兩條例外規則，差別是刻意的：

- **`defaultValue:` 選項物件是合法的逃生口。** ADR-0058 的 `rules.*` 衍生名稱本來就靠它
  解析英文，而中文那邊才有條目。
- **位置參數的字串預設值不是。** 它在每一種語言底下都渲染同一串英文，這是硬寫的英文字串，
  不是翻譯。

樣板字面值（`` t(`rules.field.${x}`) ``）不在這個守衛的範圍內：那是一個算出來的名字
（ADR-0058），由語言檔一致性那個守衛負責。

那三個 key 補進兩份語言檔，位置參數的預設值一併拿掉。

## Consequences

- 一個指向不存在 key 的呼叫點會讓 CI 紅，而不是等到有人切成中文、看到畫面上印出一個 key。
- 用位置參數塞英文預設值這條路被關掉了。要嘛補 key，要嘛用 `defaultValue:` 並且說明理由。
- 守衛只看字面 key。動態組出來的 key 仍然只能靠語言檔一致性那個守衛，這是已知的邊界，
  不是疏漏——列舉一個算出來的名字需要把算法在測試裡再寫一次，而那就是 ADR-0061 差點犯的
  「守門測試重新實作了它要檢查的規則」。
