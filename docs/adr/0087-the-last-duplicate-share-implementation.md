# ADR-0087: 最後一份重複的分享實作

## Status
Accepted

## Date
2026-08-16

## Context

ADR-0070→0073 把分享收斂成一份：一個面板、一個公開頁、一個資料端點、一個行事曆 feed。那條線的起因是一份「漂掉的分享面板複本」把同一個分享的兩個不同連結交給使用者，而 ADR-0072 是它的帳單 —— 一個**設得上去卻被完全忽略**的專案分享 PIN，擁有者收到 `{ok: true}`，鎖不存在。

寫入表面也收斂了 —— 對 SPA 而言。但 `/api/v1` 長出自己的 share facade（ADR-0042）時，是在旁邊**重新寫了一份**：自己 `uuid4()` 造 token，自己重複一次每條規則。

從 ADR-0085、0086 一路收下來，這是同類裡最後一筆。它一直被記在那兩份 ADR 的「仍然沒收的債」裡，理由是「還沒造成傷害」—— 而那正是 ADR-0070 警告的狀態：**一份還能用的複本沒有失敗症狀**。

## Decision

規則搬進 `services/share_admin.py`：什麼可以被分享、PIN 長什麼樣、expiry 怎麼存、token 由誰鑄造。兩扇門都呼叫它，拒絕由 `ServiceError` 的單一 handler 算繪（ADR-0085）。每個 router 只留自己的 404 和「誰可以問」。

測試瞄準**輸出邊界**而不是端點回應碼 —— ADR-0070 的教訓就是「複本還能用」，所以問題不是「兩扇門都回 200 嗎」，而是「從一扇門設定的分享，在另一扇門的分享會被讀取的那個公開頁上，行為一不一樣」。所以 `tests/test_share_write_parity.py` 斷言的是：v1 鑄的 token 打得開 `/share/node/{token}`；任一扇門輪替都會讓另一扇門的舊 token 失效；任一扇門設的 PIN 都讓公開頁要求 PIN。

## 收斂時撞出來的缺陷

`POST /api/v1/nodes/{id}/share/rotate-token` 用一把 `write` 金鑰呼叫，回傳的是 **`200 {}`**。

ADR-0059 的 redaction middleware 會從每一個 v1 response 剝掉 `share_token`，除非金鑰是 `admin`。所以這個端點做完了它該做的事 —— 輪替 token、**讓現行的分享連結立刻失效** —— 然後把唯一能說出新連結是什麼的欄位拿掉了。呼叫者弄壞了一個活著的連結，而且無從得知新的。

這和 ADR-0084 拒絕挖洞的那個形狀完全一樣。做法也一樣：**去符合規則，而不是在規則上開例外**。`rotate-token` 改成需要 `admin` scope —— share token 就是那個公開 URL，交出它就是授予權限。其他分享寫入（set-pin / expiry / guest-notes）回的是 `{"ok": true}`，不帶任何能力，維持 `write`。

這是把兩份實作併起來才看得見的：一份實作各自看都「正常」，是把它們放進同一個 service、再問「同一個請求兩邊答案一樣嗎」的時候才掉出來的。

## Consequences

**好的：**

- 分享的每一條規則只有一處。第三扇門加進來時，拿到的是同一組拒絕和同一個 token 產生器。
- 一個已經上線的缺陷關掉了：不會再有人輪替掉自己的分享連結卻拿不到新的。
- ADR-0070→0073 那條線真的結束了，沒有剩下的複本。

**要付的代價：**

- `rotate-token` 從 `write` 升到 `admin` 是一個**破壞性變更**。任何拿 `write` 金鑰輪替分享 token 的既有整合會開始拿到 403 —— 不過它原本拿到的是一個空物件加上一條壞掉的連結，所以這個「破壞」是把一個沉默的失敗換成一個明確的失敗。
- `share_admin` 的 `rotate_token` 自己 commit，和其他 `*_admin` service 一致，但這表示它不能和呼叫端的其他寫入放進同一個交易。目前沒有呼叫端需要那樣做。
