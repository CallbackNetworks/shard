# ADR-0068: 一個專案的大小只有一個答案

## Status
Accepted

## Date
2026-08-07

## Context

ADR-0065 把彙總改成整棵子樹，但只改了專案頁、容器頁與目標頁。那份 ADR 自己記下了還沒收斂的部分：

> 專案進度這條規則在程式碼裡還有好幾份各自為政的拷貝（`share.py`、`search.py`、`external_api/helpers.py`、`external_api/stats.py`、`scheduler.py` 的摘要信、`notifier.py`），它們維持直接子節點的算法。

實際去數，同一個問句「這個專案有多大」在程式碼裡有 **11 個各自實作的答案**。而且它們不只在「要不要算巢狀容器」上分歧，在「要不要把子任務算成一個任務」上也分歧：

| | 算巢狀容器裡的任務 | 把子任務算成一項 |
|---|---|---|
| 專案頁 / 容器頁 / 目標頁 | ✅（ADR-0065 之後） | ❌ |
| 公開分享連結、`/api/v1` 專案讀取、`/api/v1/*/stats`、`/api/v1/summary` | ❌ | ✅ |
| 站內搜尋、`/api/v1/search` | ❌ | ✅ |
| 每日摘要信、每週彙整、AI 助理摘要 | ❌ | ❌ |
| 通知承載（webhook / email） | ❌ | ✅ |

於是一個有 6 個任務、3 個子任務、外加一個巢狀容器（2 個任務）的專案，在 app 裡是 `8`，在分享連結裡是 `9`，在每日摘要信裡是 `6`。三個答案，全部都「對」，因為它們各自回答了不同的問題。

這是 ADR-0056 的同一個病：**一份規則被抄成很多份，於是它們一定會分岔。** 差別只在那次分岔的是「欄位裡該裝什麼」，這次分岔的是「一個專案有多大」。

## Decision

**專案的大小＝它整棵 `contains` 子樹裡的 top-level 任務。一條規則，所有回報數字的地方都讀它。**

1. 新增 `graph.subtree_task_ids/subtree_task_views(db, id, top_level_only=…)`：`contained_task_ids` / `tasks_in_project` 的子樹版本。所有**回報**用的讀取端改用它，成員檢查（「這個任務屬於這個專案嗎」）維持直接子節點——那是在問一條邊，不是在問子樹。

2. 數字用 `top_level_only=True`（或直接用 `container_subtree_stats`）：父任務與其子任務是同一個工作單位。這對外部 API 是**契約變更**——即使沒有巢狀，一個有子任務的專案在 `/api/v1` 回報的 `total_tasks` 會變小——但變成和 app 顯示的一致，而「和使用者看到的一致」比「和上週的自己一致」重要。

3. **清單與數字分開**：`/api/v1/summary` 的待辦清單仍然包含子任務（agent 問「我接下來做什麼」時要看得到），只有計數器套用 size 規則。清單服務它的讀者，數字服務那一條規則。

4. `/api/v1/nodes/{id}/subtree` 讓外部客戶端（含 MCP）看得到下一層容器；MCP 增加 `get_container_subtree` 工具（21 個工具）。專案範圍受限的金鑰只會拿到自己看得到的子容器。

5. `tests/test_progress_agreement.py`：一個專案，工作分散在直接子任務、子任務、與一個巢狀容器，然後**逐一詢問每一個回報面**——app、搜尋、分享連結、v1 專案讀取／stats／search／summary、身分中心、通知承載、AI 助理摘要。這條測試是這個決定的執行機制：下一個抄第 12 份算法的人會在這裡被擋下來。

## Consequences

正面：

- 同一個專案在任何地方都是同一個數字。上一版的三個答案（8/9/6）收斂成一個。
- 每一個回報面的內部也一致了：`/api/v1/*/stats` 的 `by_status` 總和現在等於它自己的 `total_tasks`（以前不等）。
- 新增回報面時有現成的正確函式可用，而 agreement 測試會抓到沒有用它的人。

代價：

- **`/api/v1` 的數字會變**：有子任務的專案 `total_tasks` 變小，有巢狀容器的專案變大。外部儀表板若寫死了預期值會看到跳動。這是刻意的，理由如上。
- 公開分享頁的表頭數字現在算到巢狀容器裡的任務，但清單只列這個專案自己持有的（與 app 的專案頁一致）；分享頁因此也會出現「數字大於清單長度」的情形。
- 尚未收斂：`analytics.py` 的圖表仍以直接子節點過濾任務（它問的是「畫哪些點」，不是「多大」，但巢狀時同樣會漏）；`ical` 訂閱同理。兩者都是既有行為，不在本次範圍。
- 每一次回報都多走一次子樹遍歷（`descendants_of` 已在 ADR-0065 改成一層一批查詢，所以成本是每層一次查詢，不是每節點一次）。
