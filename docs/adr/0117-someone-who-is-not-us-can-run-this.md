# ADR-0117: Someone who is not us can run this

## Status
Accepted

## Date
2026-08-27

## Context

Shard is a single-user system *per instance*, and the intent is that other people run
their own — not that many people share one. That rules out accounts, tenants and a
permissions matrix, and it makes exactly one thing matter that had never been measured:
what a stranger has to do between finding the repo and seeing the app.

Today the answer is: clone, then work it out. `docker-compose.yml` is the dev stack —
it bind-mounts the checkout over `/app`, runs Vite on 5173 with hot reload, and is not
what anyone would leave running. ADR-0108 retired `docker-compose.prod.yml` and moved
production to a compose file *generated by the CD job* on the deploy host. That decision
was right and stays: a compose *override* can never remove the dev stack's bind mounts,
so a file that layers on top of the dev stack cannot describe production.

But "no override file" was read as "no file". The consequence is that the only complete,
runnable description of a production Shard lives inside `.github/workflows/ci.yml`, in a
heredoc, referencing images in a registry that requires `docker login` with credentials
only this project has. A person who is not us cannot deploy Shard at all — not because
anything is missing, but because the recipe is not a file.

The comparison that surfaced this: beads installs as one Go binary, Lovelace as one
desktop app. Shard has more capability than either and would still lose every adoption
race, because in this category the install step decides and nothing else gets read.

## Decision

Add `docker-compose.selfhost.yml` — a standalone, self-contained stack, not an override:

- **It builds from the checkout** (`Dockerfile.prod` for both services) instead of
  pulling. Our images live in a private registry; requiring `docker login` would put a
  credential in front of the first command. `image:` is declared *alongside* `build:`,
  so Compose builds when the tag is absent locally and `docker compose pull` still works
  if these images are ever published publicly.
- **Every value has a working default**, so a bare clone boots with no `.env` at all.
  `.env.example` remains the place to start overriding.
- **The frontend binds to loopback by default** (`SHARD_BIND`), because `AUTH_PASSWORD`
  defaults to empty and empty means no login gate. A fresh instance must not be an open
  instance; reaching it from the network is one variable, and the comment beside it says
  to set the password in the same edit.
- **It carries its own project name** (`shard-selfhost`), so bringing it up in a checkout
  where the dev stack is running does not reconcile — stop and replace — those containers.
- **`./data` and `./uploads` are both bind mounts.** The database and the attachments are
  the only state worth keeping, and someone self-hosting must be able to see and copy them
  without knowing what a named volume is.
- **The backend service keeps the name `backend`**, because `frontend/nginx.conf` proxies
  to the literal host `backend:8000`.

ADR-0108 is unchanged and not superseded. Production is still deployed by CD from a
generated file; this is a second, differently-purposed artifact, and the two do not
share a code path. The duplication is real and accepted: collapsing them would mean
either shipping our registry credentials or making CD build from source on the deploy
host, and each is worse than one file that says the same shapes twice. ADR-0070's
"one implementation" instinct applies to behaviour that can drift silently — a stack
that fails loudly at `up` is not that.

## Consequences

**Positive.** `git clone && docker compose -f docker-compose.selfhost.yml up -d` is the
whole install, verified end to end: images build, the fresh-database path creates and
stamps its own schema (`alembic_version` at head, the six built-in node types seeded),
`/health` reports the scheduler alive, the SPA and `/docs` serve, and `/mcp` is correctly
*absent* (404) until `MCP_HTTP_TOKEN` is set, per ADR-0080.

**Negative.** A third description of the stack now exists beside the dev compose and the
CD generator, and a service or variable added to production must be added here too or a
self-hoster gets a stack subtly unlike ours. There is no test pinning that; the honest
mitigation is that this file is the one a stranger runs, so it fails visibly rather than
quietly.

**Also.** First build is a few minutes on a cold cache — worse than pulling a published
image, and the price of not asking for a `docker login`. Publishing images publicly would
remove it, and `SHARD_IMAGE_PREFIX`/`SHARD_TAG` are already the seam for that.

**Uncovered by this decision.** Writing the file does not make it discoverable: `README.md`
still opens with a feature list rather than a quickstart, and still claims the MCP server
offers 20 tools where it now offers 51.
