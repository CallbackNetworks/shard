# ADR-0101: 少開一個 worker,而不是把限流做成永久的

## Status

Accepted

## Date

2026-08-18

## Context

`services/rate_limiter.py` 是記憶體內的滑動窗口計數器,程式行程內有效、重啟就清空。ADR-0098 上線公開問答助理之後,這個限流第一次守著一個「每次呼叫都是真金白銀」的端點,值得重新評估要不要做成永久的。

調查發現兩件事:這個 repo 完全沒有 Redis 或任何其他常駐狀態服務可以借;`backend/Dockerfile.prod` 的 `CMD` 寫死 `--workers 2`,不是環境變數可調——這正是「限流不準」的根本原因:兩個 worker 各自維護一份記憶體內計數,同一個 token 理論上能拿到將近兩倍的額度,純粹看請求被路由到哪個 worker。

## Decision

**把 worker 數改成 1,不是把限流搬進資料庫或加 Redis。** 這是單人個人工具,兩個 worker 換來的並行處理能力本來就用不太到;改成 1 個之後,現有的記憶體內限流變成單一、準確的計數來源,不用改一行 `rate_limiter.py` 的程式碼。

資料庫或 Redis 的方案都評估過,結論是代價比問題本身大:限流要在**每一次**被限流的請求上做原子讀寫,頻率遠高於 `ActivityLog`/`WebhookDelivery` 這類既有的高寫入表(它們一次使用者動作寫一列,不是一次請求寫一列),在 SQLite 上尤其會撞上 WAL 只能有一個寫入者的限制;Redis 則是這個 stack 裡從來沒出現過的新元件,為了「重啟後限流會重置」這種發生機率很低、後果也很小的事,不值得。

「重啟清空限流」維持現狀,刻意不解決——這是 accepted limitation,不是遺漏。

## Consequences

正面:限流變準了(不再有 worker 路由運氣造成的雙倍額度),零新程式碼、零新基礎設施。

負面與代價:少了一個 worker,理論上這個行程能同時處理的請求數變少——對單人使用的個人工具,這個代價可以忽略。真的哪天流量規模變了、需要更高並行度,這個決定要重新評估(那時候「限流准不准」跟「要不要撐得住並行請求」會是同一個問題,得一起解)。
