# ADR-0066: 一個控制項的 N 個值，不是 N 個導航入口

## Status
Accepted

## Date
2026-08-07

## Context

側邊欄的 rail 由五段組成：品牌、搜尋、可捲動的模組清單、底部的固定動作。
模組清單這一段裡，`FocusRail` 為每一個身分畫一顆按鈕，`ContainerTypesRail`
為每一個使用者自訂的容器型別畫一顆按鈕，兩者都排在 `NAV_GROUPS` 那 17 個
固定模組的**前面**。

這兩段的長度由資料決定，沒有上限。用開發資料庫（9 個身分、1 個自訂容器型別）
在 1440×900 實際量測：

- 9 顆身分頭像加上一顆「退出聚焦」＝ **378px，佔整條 rail 的 42%**
- 固定模組只剩 **4 個看得到**（總覽、階層、動態、分析）
- 目標、決策、助理、整合、工作流規則、API 金鑰、設定等 **11 項全部在摺線以下**

底部動作因為佔著自己的 grid 列而沒事，被推掉的正好是導航本身。身分再多幾個，
連第一組模組都會消失。

關鍵在於這兩段被推擠的方式並不相同，原因也不同：

- **身分聚焦**一次只能選一個，選了之後整個 app 都跟著收窄。它是**一個控制項的
  N 個互斥值**，不是 N 個去處。把它畫成 N 顆導航按鈕是分類錯誤——正因為畫成了
  導航，它才會隨資料線性長高。
- **自訂容器型別**確實每一種都是一個導航目的地，這點沒有錯。錯的是把一個
  數量無上限的集合直接攤在一條高度有限的 rail 上。

## Decision

**rail 上的每一列都必須是宣告出來的模組。任何數量由資料決定的集合，都不能直接
佔用 rail 的列。**

兩段各自依照它真正的語意收斂：

1. **身分收成單一 Focus 切換器**（`components/FocusSwitcher.jsx`）。一列顯示
   目前聚焦的身分，點開是一個帶搜尋的 popover，裡面才是完整清單。「不聚焦」
   是這個控制項的一個值，所以它是選項清單的第一列，而不是只有在聚焦時才出現的
   額外按鈕。列數從此與身分數量無關——身分愈多，可搜尋的清單反而愈好用。

2. **自訂容器型別收成單一入口**。rail 上放一個固定的 `/containers` 模組，
   型別清單移到頁面上（`pages/Containers.jsx`），每一張卡片帶著型別顏色與
   `usage_count`，點進去是原本的 `/t/{key}` 列表。型別是導航沒錯，但它的
   *清單*屬於頁面，rail 只負責那道門。

3. **Focus 切換器擁有自己的 grid 列**，位於搜尋與模組清單之間。整條 rail 只有
   模組清單會捲動，所以搜尋、聚焦控制項與底部動作三者永遠在原位。

popover 開著的時候，rail 會被 `is-menu-open` 撐開維持展開——一個錨定在 rail 上的
浮層，生命週期比開啟它的那個游標長。

## Consequences

**正面**

- rail 的高度不再是資料的函數。9 個身分或 900 個身分，rail 都是同樣的列數。
- 固定模組從「4 個看得到」變成 16 個看得到（新增 `/containers` 後共 18 個）。
- 身分清單獲得搜尋、鍵盤上下選擇、Enter 選取、Esc 關閉；原本 9 顆按鈕的版本
  只能用眼睛找。
- 「退出聚焦」不再是一顆時有時無的按鈕，選單的選取狀態直接看得出目前聚焦在誰。
- `/containers` 是一般的 `NAV_GROUPS` 項目，因此自動沿用既有的
  `sidebarOrder` / `sidebarHidden` 偏好，可以排序也可以隱藏。

**負面 / 取捨**

- 切換身分從一次點擊變成兩次（開啟、選取）。身分少的人變慢了一點；這是換取
  身分多的人還能用的代價，而後者是這個 app 多身分定位下的常態。
- 進入某個自訂容器型別同樣多了一跳。
- 18 個固定模組在 900px 高的視窗仍會讓最後一組（System）需要小幅捲動。這個
  剩餘量是**有界且使用者可控的**——模組清單是宣告出來的，並且可以在設定頁隱藏
  ——與原本隨資料成長的情況性質不同。
- 新增了一個 `is-menu-open` 的狀態耦合：rail 的寬度不再只由 hover 決定。
