# ADR-0121: 內建型別宣告的來源是程式碼，不是可改的資料列

## Status
Accepted

## Date
2026-08-28

## Context

ADR-0119 讓內建型別的宣告在部署時重新套用，並加了指紋守門，防止「改了程式碼卻忘了同步」。它明白留下一個沒解決的矛盾：那些欄位透過 API **仍然可以改**，而下一支同步 revision 會把使用者的編輯無聲蓋掉。當時的判斷是「不強制，但會蓋回去」。

追問之後，這個判斷站不住腳，因為那些欄位不只是文件：

| 欄位 | 是文件還是行為 |
|------|----------------|
| `edge_types.description` | 文件 —— 但 agent 靠它決定用哪個關係（ADR-0078） |
| `edge_types.allowed_source` / `allowed_target` | **行為** —— `graph.add_edge` 每一次寫入都照它擋 |
| `node_types.fields` | **行為** —— 決定通用編輯器畫什麼、寫什麼（ADR-0074） |

也就是說，這個狀態的實際後果是：你今天用 API 把 `governs` 的允許目標放寬，系統從此接受那些邊；三個星期後，某次**為了別的原因**、跟你的編輯毫無關係的部署帶了一支同步 revision，規則悄悄縮回去。之前建的邊還在，新的建不了，錯誤訊息說的規則跟你記憶中的設定不一樣，而且沒有任何通知。

一句過期的說明已經夠糟（正式站因此對 agent 說了幾個月的假話），一條會被無聲還原的**執行規則**更糟。

## Decision

內建型別的**宣告**在兩道門上都唯讀：

- 節點型別：`fields`
- 關係型別：`description`、`allowed_source`、`allowed_target`

守門放在 `graph_registry`，跟既有的「內建不可刪」「內建 container/task 角色凍結」「使用中不可刪」同一個地方，所以內部 `/api/graph-types` 和外部 `/api/v1/{node,edge}-types` 拿到同一個拒絕（ADR-0079 的規矩）。拒絕訊息說得出原因和後果：這是在程式碼裡宣告的，改了會被下一次同步還原。

**沒有凍結的**：`label`、`icon`、`color`，以及 `IMMUTABLE_BUILTIN_ROLES` 以外的角色。那些是你的偏好，沒有任何東西會同步它們，而且畫面上真的有按鈕。這條線跟 ADR-0119 那支 backfill 重套的範圍**完全一致** —— 它不碰的，這裡就不凍結。

**自訂型別完全不受影響。** 它們沒有第二份，所以不會漂移；宣告什麼、怎麼改，都是你的事。

## Consequences

**得到的：** 「你改了、我未來某天蓋回去」這個狀態不再存在 —— 不是靠約定，是靠改不了。規則的來源永遠是執行它的那份程式碼。

順帶把「內建」這個詞正在做的兩件事切開了：**引擎的字彙**（`contains` 不是一列資料，是彙總的骨架，程式碼指名讀它）和**我們給的預設**（名稱、圖示、顏色）。兩者原本掛同一個 `is_builtin` 旗標放在同一張表，系統分不出哪個是「關於程式碼的事實」、哪個是「可以改的預設」。這條線是第一次把它們分開。

**付出的：** 少了一個能力。實測過：正式站的每個內建型別，`label`/`icon`/`color`/`roles` 全部跟程式碼一致 —— 從來沒有人改過。而被凍結的那三個欄位，**畫面上本來就沒有任何按鈕碰得到**（`NodeTypeEditRow` 只送 label/color/roles，關係型別根本沒有編輯 UI），只有直接打 API 才改得到。

**擋不住的：** 直接改資料庫。那是你的資料庫，沒有任何機制管得著 —— 而且直接寫進去會繞過**所有**守門，包括 `IMMUTABLE_BUILTIN_ROLES`（把 `project` 的 `container` 拿掉會當場拆掉整條彙總管線）。這份 ADR 保證的是「被支援的那道門只有一個答案」，不是「這個值不可能被改」。

**沒有做的：** 沒有把 `is_builtin` 拆成兩個旗標（「引擎字彙」對「出廠預設」）。目前用兩份凍結清單表達，夠用；真要拆成資料模型上的區分，值得另開一份 ADR。
