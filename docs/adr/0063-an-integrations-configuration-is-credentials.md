# ADR-0063: 整合設定裡裝的就是憑證

## Status
Accepted

## Date
2026-08-06

## Context

`GET /api/integrations` 把每一個整合的憑證原封不動送出來。實測公開的開發環境，一個 webhook 整合的簽章金鑰就是明文躺在回應裡：

```json
{ "name": "Payments Reliability Webhook", "type": "webhook", "secret": "<15 字元明文>" }
```

不只是 `secret`。`IntegrationOut` 上有三個欄位帶著憑證：

| 欄位 | 裝的是什麼 | 誰在用 |
|---|---|---|
| `secret` | HMAC-SHA256 簽章金鑰，或 Bearer token | `notifier._build_headers` |
| `auth_config` | `{username, password}` 或 `{header_name, header_value}` | 同上 |
| `custom_headers` | 使用者自填的 HTTP 標頭 | 同上 |

一個整合存在的目的就是向別人的端點證明自己的身分，所以**它的設定本質上就是憑證**。這三個欄位加起來，足以讓讀到的人冒充這個系統對外送出簽好章的請求。

**為什麼 ADR-0059 沒有抓到。** 那一次掃的是 `Node.data`——自由格式的 JSON，沒有 schema，所以憑證藏在裡面時完全不會出現在 OpenAPI 契約上，稽核的人看契約永遠看不到。當時的判斷是「有型別的 response model 會自己說明自己」，於是沒有再看一眼。而 `IntegrationOut` 確實忠實地說明了自己：它宣告了 `secret: str | None`，然後把它送出去。**契約寫得很清楚，清楚地寫著一件不該做的事。**

（`auth_config` 和 `custom_headers` 其實又是自由格式的 dict，所以連 ADR-0059 那條「自由格式 JSON 沒人審查過」的理由也原樣適用，只是它們掛在一個有型別的模型底下就沒被歸類進去。）

現有的正確寫法就在同一個檔案往上 150 行，是 ADR-0059 為 `TaskOut` 寫的：

```python
webhook_secret: str | None = Field(default=None, exclude=True)
webhook_secret_set: bool = False
```

這又是這個程式庫反覆遇到的同一種形狀：一條規則在某一處被想清楚了，但沒有跟著擴散到下一個同類的地方。

還有一個沒被發現的原因值得記下來：**既有的測試對這件事完全沒有意見**。12 條整合路由測試沒有任何一條斷言過 `secret` 有沒有回來——不是斷言它「應該回來」而後來變成錯的，是從來沒人問過。洩漏和不洩漏都能通過。

## Decision

**憑證不離開伺服器（延續 ADR-0059），而且「把讀到的東西原樣寫回去」必須是安全的。**

第二句話是這個決定的重點。單純把欄位藏起來會製造一個更糟的陷阱：使用者打開編輯視窗、把 basic auth 的帳號從 alice 改成 bob、按儲存，前端送回一份沒有密碼的 `auth_config`，密碼就被靜靜刪掉了。**遮蔽讀取這件事，會反過來讓寫入變得危險。** 兩端必須一起設計。

規則是同一條，從兩頭讀：

1. **讀取時，設定了但不給看的值讀成 `null`，而且它的 key 還在。** 存起來的標頭值一定是字串，所以 null 不可能和真實值混淆：**key 不在 = 沒設定，key 在但值是 null = 有設定但不給看**。`secret` 是唯一需要額外布林值的欄位，因為它本來就是 `str | None`，null 已經有「沒有」的意思了——所以另外給一個 `secret_set`。

2. **寫入時，`null` 代表「維持原狀」。** 這是第 1 條的必然結果：既然不給看的值讀成 null，那 null 在寫回來時就只能解釋成不變。於是一個 GET 之後改一個欄位再 PATCH 回來的客戶端，不可能弄丟它從來沒看過的東西。

3. 要清掉一個憑證，送空字串。要移掉一個自訂標頭，就不要送那個 key。

`auth_config` 和 `custom_headers` 因此在 PATCH 時是**逐 key 合併**而不是整份取代。

**這個保護放在伺服器端，而不是靠表單自律。** 前端當然也照著做（不把 null 正規化掉），但正確性不能壓在單一個手寫的客戶端上——這正是這個程式庫一再踩到的模式。伺服器不管誰來寫，行為都一樣。

**`custom_headers` 一律全部遮蔽，不挑。** `auth_config` 有一份 key 清單可以查（`password`、`header_value` 是憑證，`username`、`header_name` 是設定，後者必須看得見才能編輯）；自訂標頭沒有。`X-Environment: production` 不是機密而 `X-Api-Token: ...` 是，而這裡沒有任何東西分得出來。代價是重打一次標頭值，另一邊的代價是送出一個 token——不對等，所以選前者。

規則放在 `services/integration_data.py`，刻意做成 `services/node_data.py` 的姊妹：同一個問題的兩個地方，讀起來應該像同一件事。

## Consequences

- 憑證不再出現在任何整合的讀取回應裡。實測：建立一個帶完整憑證的整合後，`GET /api/integrations` 的整個回應本文中找不到任何一個原始值。
- 編輯整合不會再弄丟沒看到的憑證。實測了那條真正危險的路徑：讀取 → 改帳號 → 寫回 → 資料庫裡的密碼與自訂標頭值原封不動。
- **UI 上不能再「清空欄位來刪掉金鑰」了。** 空欄位現在一律是「不變」——這是值不再顯示之後，空欄位唯一誠實的意思。要清掉得走 API 送空字串，或刪掉整合重建。這是取捨，不是疏漏。
- `notifier` 完全沒有改動，憑證照樣送到對方端點。有一條測試專門釘住這件事：遮蔽只影響讀取介面，不影響實際用途。
- 新增 12 條後端測試（`test_integration_credentials.py`）與 5 條前端測試。兩邊都做過反向驗證：把遮蔽拿掉，4 條後端測試失敗；把前端改成在開啟編輯時把 null 正規化成 `''`，2 條前端測試失敗。
  - 過程中發現自己第一版的前端測試理由是**錯的**：註解寫著「`?? ''` 換成 `|| ''` 就會洩漏」，但 `null || ''` 和 `null ?? ''` 完全相同，那個綁定從來不是關鍵——真正承載安全性的是 null 一路留在 form state 裡沒被動過。反向驗證抓到了這個誤解，註解已改成事實。**沒看過它失敗的守門測試，不能算守住了任何東西**（ADR-0061 的同一課）。
- `/api/v1` 不受影響：`SubscriptionOut` 本來就沒有把 `secret` 放進去。
- 這件事的**嚴重程度取決於 `AUTH_PASSWORD`**。開發環境沒設密碼又開著公開通道，所以憑證等於公開；正式環境有 auth 擋著，但憑證仍然會送進瀏覽器、進開發者工具、進任何能碰到那個回應的東西。ADR-0059 立的規則是「憑證不離開伺服器」，不是「憑證只給登入的人」。
- 驗證：後端 1050 passed / 1 skipped，前端 365 passed / 48 files，ruff 與 ESLint 乾淨。
