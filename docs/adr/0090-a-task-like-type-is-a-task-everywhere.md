# ADR-0090: 宣告了 task 角色，就在每一個地方都是任務

## Status

Accepted

## Date

2026-08-16

## Context

ADR-0089 的 Consequences 裡留了一條「明確沒有做」：`scheduler.py` 和 `critical_path.py` 用字面 `Node.type == NODE_TASK` 比對型別，所以宣告了 task 角色的自訂型別收不到到期提醒、也不會出現在日報／週報。當時判斷那會改變「誰會收到通知」，是一個獨立的決定。

把範圍攤開看之後，情況比那條註記更廣。ADR-0033／0035 定下的規則是：使用者在 `node_types` 宣告一個帶 `task` 角色的型別，那個節點就是一等任務。`graph` 服務層一路貫徹這件事 —— `task_type_keys(db)` 出現在 `subtree_task_ids`、`top_level_task_filter`、`task_view`、`labels_map` 等等。**但它的呼叫端沒有。** 全 app 有 28 個查詢直接比對字面型別，分佈在排程器、分析、搜尋、外部 API、assistant 工具、bulk 動作、issue 同步。

也就是說，這不是排程器一個角落的問題，而是「服務層知道規則、呼叫端各自重寫」的系統性缺口。在開發資料庫上量得到的後果：

- 分析頁算出 81 筆逾期，首頁算出 83（ADR-0089 已修分析那兩處）；
- **搜尋結果說某專案完成 2 項，專案頁說完成 3 項** —— 而 ADR-0068 的存在就是為了讓這兩個數字一致，那段程式碼上面兩行還寫著「a search hit reports the same size the project page does」；
- 到期提醒、日報、週報、SLA 升級，永遠不可能提到一個自訂型別的項目；
- 關鍵路徑分析會直接略過它們，所以一條真正的路徑可能被算短。

值得注意的是：這些查詢沒有一個是**故意**只要內建型別的。它們的語意都是「所有任務」，只是寫的時候順手把型別常數寫死了。真正該用字面型別的地方是**建立**節點（`ensure_node(db, id, graph.NODE_TASK)`，意思是「造一個內建那種」），那些不受影響。

## Decision

`graph.task_type_filter(db)` 是唯一的判準，28 個查詢全部改用它。查詢問的是「這是不是一個任務」，答案由註冊表回答，不是由一個寫死的字串回答。

**這確實會改變誰收到通知**，而那正是想要的結果：使用者宣告一個 `incident` 型別、給它 task 角色、設了到期日，卻收不到提醒 —— 那不是保守，那是漏掉。自訂型別本來就是這個產品的核心（ADR-0035、ADR-0079），一個到不了通知的一等公民不是一等公民。

守門測試 `tests/test_task_type_reach.py` 有兩個部分。一是**靜態掃描**：`app/` 底下任何一行出現 `Node.type == NODE_TASK` 這個查詢形狀就失敗，唯一豁免是 `services/graph/core.py`（規則本身寫在那裡），豁免以名單形式存在，所以新增一個必須是刻意的。二是**行為**：宣告一個帶 task 角色的自訂型別之後，搜尋結果與專案頁報出同一組數字，而且那個節點確實落在排程器的到期提醒候選集合裡。

靜態掃描這一招沿用 ADR-0044 的做法，理由也相同：這個錯誤的症狀是「一個數字偏小」或「一封信沒寄出」，兩者都不會有人在當下發現。

## Consequences

正面：宣告 task 角色的自訂型別現在真的是任務 —— 會被提醒、會進日報週報、會被 SLA 盯、會出現在關鍵路徑、會被搜尋正確計數、會出現在外部 API 的任務清單與相依關係裡。ADR-0068 的「一個專案只有一個大小」對混合型別的專案也成立了。而且服務層與呼叫端終於講同一句話。

負面與代價：**通知量會變多**，程度取決於有多少自訂 task-like 型別的節點帶到期日 —— 對已經在用自訂型別的資料庫，這是一次行為改變，第一次跑排程時可能會收到一批遲來的提醒（那些項目本來就逾期，只是從來沒被通知過）。另外 `task_type_filter(db)` 每次呼叫都要查一次型別註冊表；`task_type_keys` 已有的快取涵蓋這一點，但這是一個新的、遍佈熱路徑的相依。

沒有動的：`ensure_node(..., graph.NODE_TASK)` 這類**建立**節點的位置維持字面型別，因為它們的語意就是「內建那一種」；靜態掃描只針對 `Node.type ==` 這個查詢形狀，不會誤傷它們。
