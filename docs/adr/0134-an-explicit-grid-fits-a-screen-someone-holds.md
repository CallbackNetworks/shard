# ADR-0134: 明確宣告的 grid 要塞得進真的有人拿在手上的螢幕

## Status
Accepted

## Date
2026-08-31

## Context

ADR-0133 修掉了決策頁深層群組的縮排複利之後，使用者回報「在手機上決策卡片還是會被
裁切」。實際量到的範圍比手機大得多。

`.kt-decision-room` 的宣告是：

```css
grid-template-columns: 230px minmax(320px, 0.9fr) minmax(360px, 1.1fr);
gap: 14px;
```

三個 track 的下限加上兩道間隙 = **938px**。這是「這條宣告要被遵守，內容盒至少要有多寬」
的硬性門檻，而頁面只有在視窗約 1180px 以上才拿得到那麼寬。

`repeat(auto-fill, minmax(260px, 1fr))` 不會有這個問題 —— 容器變窄時瀏覽器用**少畫一欄**
來滿足下限。**明確列出的 track 沒有這個逃生門**：下限就是下限，達不到就整個 grid 長到
容器外面去。而這三欄都是 `overflow: hidden`，所以溢出的部分不換行、不能捲、也不縮 ——
第三欄直接被切掉，第二欄的卡片沿著右緣被剖開。

從 600px 掃到 1024px 實測（`roomOverflow` = 容器溢出像素）：

| 視窗 | `is-mobile` | 溢出 |
|------|-------------|------|
| 360–560 | 是 | 0 |
| 600 | 否 | 370 |
| 768 | 否 | 202 |
| 900 | 否 | 318 |
| 1024 | 否 | 194 |

600px 是分界，因為 `useBreakpoint` 在那裡不再回報 `mobile`，`is-mobile`（唯一那條把
grid 收成一欄的規則）就跟著失效。**所以壞掉的不只是手機，是每一台平板、每一支橫著拿的
手機，以及一台 1024px 的筆電。**（≥800px 的 `mainOverflow` 更大，是因為側欄佔掉 224px。）
它被當成手機問題回報，只是因為手機是最容易注意到的那一端。

## Decision

**一、明確宣告的 track 一律 `minmax(0, …)`。** 要畫幾欄是媒體查詢的職責；track 本身
必須永遠塞得下。`.kt-decision-room` 改成 `230px minmax(0, 0.9fr) minmax(0, 1.1fr)`，
`is-mobile` 的 `1fr` 也改成 `minmax(0, 1fr)`（`1fr` 等同 `minmax(auto, 1fr)`，auto 的
下限一樣會撐破容器）。

**二、欄數改由 CSS 決定，不再只靠一個 JS 斷點。** 版面和它需要的寬度寫在同一個地方：

- `> 1180px` — 三欄，跟以前一樣。
- `860–1180px` — 兩欄卡片，console 從 230px 的側欄變成橫跨頂端的橫幅。它本來就只是
  計分板加篩選器，寬排讀起來反而更好，而且把寬度整個還給兩欄卡片。
- `< 860px` — 一欄。再窄下去並排兩欄卡片會讓標題變成一行一個字，那正是 ADR-0122 把
  動作列搬下來所要解決的寬度問題。

`is-mobile`（JS，600px）保留，它現在只是最窄那一段的其中一條規則，不再是唯一的防線。

**三、手機上縮排減半。** `DecisionGroup` 每層 11px → 7px（`max-width: 600px`）。在
330px 寬的欄位裡，四層 `contains` 軌跡原本吃掉卡片的五分之一。

## Consequences

- 600px 到 1180px 之間現在有一個真正設計過的版面，而不是「桌面版被切掉一塊」。
- 三欄版面在 1180px 以上完全沒變。
- console 在中間尺寸不再是 sticky 側欄；捲動時它會捲走。可接受：那個尺寸下垂直空間
  本來就比水平稀缺，而且篩選器就在頁面頂端。
- `src/__tests__/gridTracksFit.test.js` 掃描全部 CSS，把每一段明確 track list 的 px
  下限加總，超過 600px（比任何直握的手機或小平板都寬）就失敗，並把那條宣告印出來。
  門檻底下的 px 下限視為媒體查詢已經處理過的真實版面決策 —— Dashboard `.commandHero`
  的 260px 側欄在 900px 收成一欄，就是這一類。
- 這條規則沒辦法靜態判斷「這個容器在這個斷點下實際有多寬」；它只能斷言「這條宣告在
  任何人真的拿得到的螢幕上都塞不下」。要抓真正的溢出，還是得在瀏覽器裡量 —— 這次就是
  掃 11 個寬度量 `scrollWidth - clientWidth` 才找出範圍的。
