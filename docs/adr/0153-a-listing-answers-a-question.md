# ADR-0153: 一份清單要回答的是一個問題，不是印出一張資料表

## Status
Accepted

## Date
2026-09-05

## Context

ADR-0150 把 Data 模組四頁併成兩頁，替 Explorer 補了搜尋框、真正的總數、和可以就地編輯的關係。那次修掉的是「找不到東西」。這次修的是找到之後：**這一頁把每一列的事實全部丟掉了，而且找到了也做不了什麼。**

### 一、每一列的事實早就在線上，畫面只畫了標題

`NodeOut` 每一筆都帶 `status`、`priority`、`start_date`、`due_date`、`updated_at`、`data`。列上畫的是型別籤 + 標題 + 一條 ancestry。所以在 144 筆任務的清單前面，「哪些做完了」「哪一筆一年沒動」「哪一筆根本沒接上任何東西」——三個問題都不在畫面上，而三個答案都已經在回應裡了。

### 二、只有一種排序，而它把新東西排到最後

後端固定 `ORDER BY position, created_at`，兩個門都沒有第二個選項。所以剛剛建好的節點排在最後；過了第一頁，除非你已經知道它的標題，否則從這一頁到不了它。一頁關於資料本身的畫面，最常問的順序就是「最近動過的」。

### 三、頁面印出 id，卻不收 id

右欄大方印著 `type · id`，而 `query` 是 `Node.title.ilike`。把畫面剛剛給你的東西貼回搜尋框，結果是零筆。

### 四、`?loose=1` 是分流用的篩選，而分流一次只能做一筆

dev 資料庫 41 筆散落節點，正式站同一形狀。要歸檔它們的唯一方式是選一筆、開一次選擇器、掛一條邊，重複四十一次。

### 五、內建型別在這頁不能建也不能刪，而理由是錯的

程式碼裡寫著 `readOnly = !!typeMeta?.is_builtin`，註解說「entity-backed builtins reject generic create/delete」。**不成立。** `node_admin.create` 只檢查型別存不存在，`DELETE /nodes/{id}` 沒有任何 builtin 守門，而 `dispatch_node_deleted` 對容器角色會走 `delete_container`（ADR-0043）、對任務會走 `delete_task_tree`、側表清理由 ADR-0131 負責——這條路就是每一種第一級實體**唯一**的寫入面（ADR-0040→0043）。代價很具體：散落篩選找得出那 41 筆孤兒（其中 22 個 project、8 個 goal），而這一頁一個都清不掉。

### 六、清單的規則有兩份，而且已經漂了

`/api/nodes` 和 `/api/v1/nodes` 各自手寫了同一段查詢。ADR-0150 給內部那份加上 `unfiled` 和 `offset`，外部那份留在原地——所以 agent 問不出眼前這一頁正在問的問題。這是 ADR-0070/0087 那條線的老形狀：兩份不會壞，只會各自漂移。

### 七（做的時候才發現的）：散落的定義只看了兩條軸的其中一條

補上「這一列有幾條邊」之後，dev 的散落清單長這樣：

| 邊數 | 筆數 |
|---|---|
| 0 | 11 |
| 1 | 22 |
| 2–4 | 7 |
| **21** | **1** |

那個 21 是 `身分 / ChungChen`，透過 `owns` 持有 21 個專案。九個身分全在散落清單裡，每一個都擁有一到二十一個專案。ADR-0150 寫的規則是「上面沒有東西、下面也沒有東西」，實作只問了 `is_containment`——而正式站的階層正是用另一條軸建的（ADR-0095：`owns` 說的是「誰的」，`contains` 說的是「住在哪」）。**於是那個 ADR 親口引用的失敗——「一個清不完的收件匣，提示還叫你把根接到別人底下」——原封不動地在隔壁那條關係上活著。**

## Decision

**一、清單的規則收成一個 service。** `services/node_listing.py` 持有 filter 與 order，兩個門都呼叫它；各自留下的只有真正屬於「門」的東西（v1 的 scope 檢查與金鑰可見範圍）。順帶讓 v1 拿到 `unfiled` / `offset` / `sort` / `status`。非法的 `sort` 是 422，不是靜默退回預設值——會被忽略的控制項只是裝飾。

**二、`sort` / `status` / id 搜尋。** `sort` 四種（`recent` 預設、`created`、`title`、`position`）。`status` 是逗號分隔的聯集，並且收 `none` 這個字面值——NULL 是一個真正的狀態（ADR-0142 就是從那些列上長出來的），一個講不出它的篩選會把最值得看的那一堆藏起來；「沒有這個篩選」和「篩選那個不存在的值」是兩個問題，空字串分不出來。`query` 從 8 個字元起同時比對 id 前綴：一個字母的前綴不是搜尋，是在抽樣字母表。

**三、總數是數出來的，狀態清單是服務出來的。** `GET /nodes/facets` 回 `{total, status: [{value, count}]}`。`total` 是套用了每一個篩選之後的 COUNT，所以分頁知道自己在哪裡、什麼時候到底，不必從「這頁滿了」去推。`status` 那份清單刻意用 COUNT 產生而不是寫死（ADR-0056）：task 是 todo/in_progress/done/failed、project 是 active/archived、decision 是 proposed/accepted/deprecated/superseded，自訂型別則是「你實際寫進去的東西」——dev 一共 12 種。沒有一份固定的詞彙表可以照抄。facet 的計數刻意**不**套用 status 篩選本身，否則它會塌成已經選中的那一個，旁邊就沒有東西可以切換了。

**四、每一列說得出自己是什麼。** 狀態點、它住在哪裡、**它有幾條邊**、上次動過的時間。邊數走 `GET /graph/edge-counts?ids=`，跟 ancestry 同樣按 id 批次（ADR-0094：呼叫端永遠是一頁列，一列一個請求就等於整頁都不問），並且共用同一個 200 的上限與同一份 chunk 邏輯——被截斷的回應在這裡會被讀成「這個節點沒有連上任何東西」，那是一句斷言，不是一個缺口。0 標紅，因為那就是你來這一頁要找的東西，而且它抓得比 `loose` 多：`loose` 只找上面沒有**而且**下面也沒有的。

**五、整批動作，而且逐筆回報。** 勾選 + 一次「歸檔到」或「刪除」。**刻意不開新端點**：這裡的每一條邊、每一次刪除，兩個門本來就各有一次呼叫，所以整批端點是便利，不是能力，而 ADR-0085 那條規則管的是能力。契約沿用匯入那一套（ADR-0092）：逐筆套用、回報 `{ok, failed}`——一批裡可以有不同型別，不同型別的合法父節點也不同，一筆被拒不該連累另外四十三筆。

**六、內建型別在這裡跟其他資料一樣。** 拿掉 `readOnly`，換成一行說明：它有自己的頁面、那裡的東西更多。刪除確認會唸出標題。

**七、散落跨兩條軸。** `unfiled_node_ids` 的「下面沒有東西」現在同時看 containment 與 `owns` 的**出向**邊。只看出向：被擁有說的是「你是誰的」不是「你住哪」，所以一個有人擁有、沒人歸檔的專案**仍然**散落——那正是這個篩選找到的絕大多數（41 → 32，消失的 9 筆全是身分）。

## Consequences

- Data 頁現在能回答四個它以前答不出來的問題（這是什麼狀態、多久沒動、有沒有接上東西、住在哪裡），而且答案全部來自本來就在回應裡的欄位。
- 兩個門對「列出節點」給出一模一樣的答案，連拒絕的字串都一樣（`tests/test_node_listing.py` 用同一個 query 同時打兩邊比對）。agent 因此拿到 `sort`/`status`/`unfiled`/`offset`——這是這次唯一擴張的能力面，而它擴張的方向是「補上內部門早就有的」。
- 每頁多兩個請求（facets 與 edge-counts），兩個都是批次的，都會隨列表的 invalidation 一起失效。
- **在這一頁刪掉一個專案，跟在專案頁刪掉它是同一件事**，包含 ADR-0131 的整套側表清理。這是刻意的：不能清的收件匣不是收件匣。風險是這一頁的刪除按鈕離「一列資料」很近，所以確認訊息唸出標題，整批刪除唸出筆數。
- 散落的定義改了，`?loose=1` 的結果會變小。任何依賴舊定義的東西沒有——它只有這一個消費端。
- `nodeExplorer.readOnlyHint` / `loadMore` / `countOf` 三個 i18n key 退場，`countRange` 取代 `countOf`：以前有兩句話（沒縮小時講型別總數、一縮小就改講「顯示 N 筆」），因為以前只知道兩個事實中的一個。現在只有一個事實。
- Guide 第 16 章與 `17-node-explorer.png` 一起更新（ADR-0148：圖是產生的，不是收藏的）。
