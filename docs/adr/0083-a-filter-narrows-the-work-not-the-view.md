# ADR-0083: 篩選縮小的是工作，不是某一個檢視

## Status
Accepted

## Date
2026-08-15

## Context

專案頁有六個分頁——Issues、Board、Timeline、Calendar、Table、Cycles——但只有 Issues 拿得到篩選後的任務。`ProjectDetail.jsx` 把 `filteredTopTasks` 交給 Issues 的列表，`BoardView`、`CalendarView`、`GanttChart`、`TableView` 收到的則是**未經過濾的 `tasks`**。更糟的是那條篩選列本身也寫在 Issues 分支裡，所以切到 Board 之後，畫面上不但多出了剛剛被篩掉的任務，連「有沒有篩選在生效」這件事都看不到了。

這不是「某個檢視忘了套篩選」的個案，而是把篩選當成 Issues 這個檢視的私有設定的結果。使用者的意圖是「我現在只想看待辦的高優先任務」——那是對這個專案的工作範圍下的判斷，跟他選擇用看板還是甘特圖來看它無關。

同一個位置還藏著第二件事：`useSearchParams` 在整個 codebase 出現 **0 次**。分頁只在掛載時從 `getUiPrefs().defaultView` 讀一次，七個篩選軸全是元件區域狀態。實際後果是：切到 Board、點進一個任務、按上一頁——回來的是 Settings 設定的預設檢視，不是剛才那個；重新整理，篩選全沒；想把「這個專案目前逾期的東西」傳給別人看，做不到，因為那個狀態沒有位址。

`uiPrefs.defaultView` 被當成了真相來源，但它其實只該是「網址沒說話時用哪一個」。

## Decision

**一、篩選作用在資料上，不是作用在某一個檢視上。**

篩選列從 Issues 分支提升到分頁內容之上，對所有任務分頁渲染（Cycles 除外——週期不是任務）。四個檢視統一接收同一組經過篩選的集合。Issues 保留它既有的「搜尋時連子任務一起找」行為，其餘檢視拿的是同一組條件套用在完整任務列表上的結果。

只有 bulk 選取模式維持只在 Issues 出現：勾選框是 Issues 列表畫的，在其他分頁給出這個開關會是一個按了沒作用的按鈕。

**二、一個工作檢視的狀態存在網址裡。**

分頁與七個篩選軸改由 query string 承載（`?tab=board&status=todo&priority=high`）。`all` 與空字串代表「沒有這個篩選」，所以不寫入網址——網址只帶真正設定過的東西。切換分頁是導覽，用 push；調整篩選用 replace，否則上一頁會一個字一個字地倒退。

`uiPrefs.defaultView` 降級為網址沒指定時的預設值。

順帶收掉同一處的三個缺口：`agent` 這一軸被提供為篩選條件，卻既不會被儲存的檢視存下、也不會被還原；儲存檢視的名稱是用 `window.prompt` 問的；匯入 JSON 失敗時跳的是 `alert('Invalid JSON')`，不說是哪裡錯。前者補上，後兩者改成頁面內的欄位與行內錯誤訊息。

## Consequences

正面：

- 切換檢視不再會默默改變你正在看的東西。這是這次修補裡最實際的一項——它原本會讓人對著 Board 上的任務數量產生錯誤結論。
- 專案的某個工作視角現在有位址：可以貼給別人、可以加書籤、重新整理不會掉、上一頁會回到上一個檢視。
- `tests/../ProjectDetail.test.jsx` 對四個檢視問同一個問題，任何一個檢視繞過篩選都會紅。這條測試是負面對照過的：把 `BoardView` 改回吃 `tasks` 會立刻失敗。

負面與代價：

- 網址變長，而且是使用者看得見的。這是刻意的取捨——可讀性換來的是可分享性；`all` 不寫入就是為了讓它不要太醜。
- 篩選狀態現在會進入瀏覽器歷史（即使用 replace，第一次設定仍會留下）。跨分頁的 Back 行為比先前複雜。
- 篩選列在 Timeline 與 Calendar 上佔掉一點垂直空間，這兩個檢視原本是滿版的。
- 每個檢視現在都可能顯示空集合。Issues 有自己的空狀態文案，Board/Table/Calendar/Timeline 各自的空狀態沒有為「因為篩選而空」寫過文案——它們會看起來像沒有資料。這一項沒有在這次處理，記在這裡。
