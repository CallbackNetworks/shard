# ADR-0126: 決策要按「它住在哪裡」歸檔，而且大量湧入時預設是收起來的

## Status
Accepted

## Date
2026-08-29

## Context

ADR-0118 把決策記錄從「掛著 `data.type="decision"` 的 label」升級成真正的節點型別，
ADR-0122 讓 `governs`／`supersedes` 這兩條關係畫得出來也建得起來。兩件事都做對了關係，
但沒有人處理過**量**。

決策頁面把記錄攤成三欄：PENDING QUEUE、LINEAGE、STANDALONE。每一欄都是一條依伺服器回傳
順序排下來的卡片流。正式站現在有 103 筆決策，其中 80 筆 accepted、11 筆 superseded、
12 筆 proposed；**supersedes 邊只有 2 條，governs 邊只有 1 條**。也就是說：

- LINEAGE 欄能畫出來的結構，總共涵蓋 5 筆記錄。
- STANDALONE 欄是 84 筆一模一樣的卡片，一路往下捲大約一萬像素。

同時，決策**是節點**，所以它住在某個地方。問 `GET /graph/ancestry`（ADR-0094）就知道：
那 103 筆分佈在 **16 條不同的 `contains` 路徑**、橫跨兩個 organization，其中還有
`organization → project → repository` 這種三層的。頁面對這件事的呈現只有一樣東西——
卡片上一行灰色的專案**名字**。上面那層完全不存在於畫面上。

所以使用者看到的是「一大坨」，而且「看不出上下層關係」：畫面上唯一的結構是取代鏈，
而取代鏈在真實資料裡幾乎不存在；真正存在的結構是容器階層，而它一格也沒畫。

## Decision

**每一欄都按決策所在的容器階層歸檔，而不是按伺服器回傳順序攤平。**

- `utils/decisionRoom.js` 的 `buildDecisionGroups(lineages, ancestry)` 把 ancestry 的
  trail 摺成一棵 trie。因此「一個 organization 底下四個 project」是**一列**，不是四段
  重複的麵包屑。分組的 `total` 數的是**記錄**、不是 lineage：一條三筆的鏈就是 3，
  標題寫 1 而底下三張卡是 ADR-0068 要防的那種不一致。
- 一條鏈歸在**鏈首**所屬的群組。`SupersedePicker` 只提供同專案的候選，所以鏈不會跨群組，
  但也不該被拆到兩個群組去。
- `components/decisions/DecisionGroup.jsx` 是遞迴的。寫死三層就是 ADR-0069 從結構圖裡
  拔掉的那個東西。
- **超過 `AUTO_EXPAND_LIMIT`（24）筆的區塊，所有群組預設收起。** 一個區塊一條規則，
  套用到每一層：低於門檻時整頁跟以前一樣，只是歸了檔；高於門檻時那一欄就是一份容器清單，
  你一次打開一個。改成「依群組各自判斷」在往下鑽時比較好看，但在最要緊的地方比較糟——
  最大的那個專案，正是那個會拿 24 張卡片迎接你的。
- 容器的顏色只進**小圓點**，絕不進文字。這是 `AncestryTrail` 已經在遵守的規則，理由是
  ADR-0088 的：使用者自選的色相在任何一個主題下都沒有對比度保證。
- 主控台加一個純文字搜尋框。它縮小的是**集合**，計分板、鏈、群組全部由縮小後的集合推導，
  否則就會出現一個數字旁邊配著一份它描述不了的清單。
- 沒有任何容器包住的決策落在 `loose`，照樣畫出來。「沒有上層容器」是圖的一個真實狀態，
  不是把記錄丟掉或替它捏一個父節點的理由。

順帶修掉兩件在同一輪冒出來的事：

- `getAncestry` 現在會依伺服器的 `MAX_IDS`（200）自動分批。原本呼叫端問超過 200 個 id
  時，只會拿到前綴的答案，而少掉的那筆讀起來是「這個節點不住在任何地方」，不是「你問太多了」。
- 搜尋沒有結果時不再顯示「建立第一筆決策」的空狀態。那個空狀態現在只在**真的一筆都沒有**
  時出現，不會蓋在一百筆決策上面。

## Consequences

正面：

- 正式站的 STANDALONE 欄從 84 張卡片（約一萬像素）變成 16 列可掃描的容器，每列帶著數量。
  湧入更多決策時增加的是**列數**，不是捲動距離。
- 上下層關係第一次出現在這個頁面上：organization、goal、area、repository 這些層級都各自
  是一列，展開才看得到底下的東西。
- 決策頁跟結構圖、看板、儀表板遵守同一條「在可見集合內解析」的規則（ADR-0069、ADR-0094）。

負面與取捨：

- 多打一支 `GET /graph/ancestry`。用整批、且以**未過濾**的 id 集合當 query key，所以
  搜尋框每打一個字不會重打一次請求。
- 一筆決策若有多個 `contains` 父節點，只歸在**第一條 trail** 底下——這跟相容欄位
  `project_id` 挑父節點的規則是同一個（依 `position`、`created_at`）。歸進所有父節點會
  讓同一張卡片在畫面上出現兩次，那比少畫一條路徑更糟。
- 群組的展開狀態不持久化。它是閱讀當下的狀態，不是設定。
- `AUTO_EXPAND_LIMIT` 是一個數字，不是一條原理。24 大約是一欄的高度；它可以改，改動時
  唯一要守的是「一個區塊一條規則」。
