# 自動化規則

如果發生了這件事，就去做那件事。規則跑在伺服器上，所以不管你有沒有開著 app 它都會運作。

![工作流程規則](/guide/13-workflow-rules.png)

## 三個部分

**觸發條件** —— 要盯著什麼：

| 觸發 | 什麼時候發生 |
|---|---|
| `node.created` | 任何東西被建立——任務、專案、決策 |
| `node.updated` | 任何東西被改動 |
| `node.deleted` | 任何東西被刪除 |
| `edge.added` | 兩個東西被連起來 |
| `edge.removed` | 一條連線被移除 |

注意這些講的是**一般的「東西」**，不是特指任務。規則可以對「一個專案被歸到某個身分底下」做出反應，或對「一筆決策被連到它管轄的工作」做出反應——不只是任務上某個欄位變了。

**條件** —— 你在意的是那些事件裡的哪些。你可以比對東西本身（型別、狀態、優先度、標籤、標題），也可以比對**什麼變了**：哪個欄位動了、連的是哪一種關係、你的東西在那條關係的哪一端。所以「當一個任務被搬進某個專案時」表達得出來，「當一個任務的優先度被調高時」也表達得出來。

**動作** —— 要做什麼：改狀態或優先度、加上或移除標籤、指派、發通知。

## 試跑

存檔之前先跑一次。試跑會拿你**現在真正的資料**去評估這條規則，並回報它本來會做什麼。

這個每次都值得用。寫出一個「比對到所有東西」或「什麼都比對不到」的條件很容易，而在事情發生之前，這兩種看起來一模一樣。

## 怎麼讀那兩個計數

每條規則會顯示兩個數字：跑了幾次，以及真的改了東西幾次。

**這兩個差很多的時候，去看那條規則。** 一條一直觸發卻什麼都沒改的規則，看起來跟一條正常運作的完全一樣——同樣是綠的、計數同樣在長——而第二個數字是唯一分辨得出來的東西。

## 規則不會連鎖

規則做出的改動不會觸發其他規則。這是刻意的：連鎖的規則會產生迴圈，而在一份「每一條單獨看都很合理」的清單裡，那個迴圈非常難看出來——它通常是以「失控」的形式被發現，而不是以「一個錯誤」的形式。

## 規則還能在哪裡管理

這一頁上的所有東西，透過 API 和給 AI 代理也都做得到。腳本可以建立、編輯、執行和刪除規則——這件事有意義，因為一個能永遠執行每一個動作、卻連一個都自動化不了的代理，只有一半的用處。
